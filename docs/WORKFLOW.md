# Совместная разработка: ветки, PR, конфликты, тест, прод

## Ветки

| Ветка | Назначение | Версия (2–3 цифры) | Деплой |
|--------|------------|-------------------|--------|
| **`main`** | Интеграция: сюда вливаются фичи через PR | **Авто** после merge ([VERSIONING.md](./VERSIONING.md)) | Локально / dev |
| **`staging`** | Тестовый стенд: только проверенный снимок с `main` | **Та же**, что в `main` (повторно не bump) | Тестовый сервер |
| **Тег / прод** | Внешний стабильный срез | **1-я цифра** вручную ([ADMIN.md](./ADMIN.md)) | Прод |

```text
feature/* ──PR──► main ──(+бот chore(version))──► PR ──► staging ──► тест-стенд
                      │                                              │
                      └──────────────────────────────────────────────┘
                                    позже: прод (ADMIN)
```

---

## Обычный день (фича)

1. `git checkout main && git pull`
2. `git checkout -b feature/краткое-имя`
3. Код, коммиты, push ветки
4. GitHub → **Pull request → `main`**
5. Ждёте **CI (build)** — зелёная галочка
6. Если **«This branch has conflicts»** — конфликт **до** merge (см. ниже)
7. Ревью → **Merge**
8. Бот (если нужно) коммитит `chore(version): bump to v…` в `main`
9. У партнёра: `git pull origin main`

**В `staging` и на тест ничего само не попадает** — только когда создадите PR `main` → `staging`.

---

## Вывод на тестовый стенд

Когда `main` готов к проверке на стенде:

1. PR **`main` → `staging`** (база `staging`, head `main`)
2. Разрешить конфликты, если есть (редко, если `staging` регулярно обновлять)
3. Merge → деплой с ветки **`staging`** (настройка сервера — [DEPLOYMENT.md](./DEPLOYMENT.md))
4. Версия на стенде = версия в `main` (из «О программе» / `package.json`)

Отдельного bump версии при merge в `staging` **нет** — иначе тест и интеграция разъедутся.

## Конфликты: когда и как

| Этап | Что видите | Что делать |
|------|------------|------------|
| PR в `main` | GitHub: **Can’t merge**, conflicts | Локально: `git checkout feature/…`, `git merge main`, правка `<<<<`, `git push` |
| PR `main` → `staging` | То же | `git checkout staging`, `git pull`, `git merge main` в PR-ветку или в `staging` по инструкции GitHub |
| После merge | Нет «тихих» конфликтов в git | — |
| Доска Retrogen (409) | Два редактора одной комнаты | Логика приложения, не git |

**Защита ветки** (см. [GITHUB_BRANCH_PROTECTION.md](./GITHUB_BRANCH_PROTECTION.md)):

- в `main` нельзя merge с конфликтами (GitHub не даст кнопку);
- можно требовать **актуальную ветку** (`main` обновлён перед merge) и **зелёный CI**.

Автоматически конфликты **не решаются** — только показываются; исправление и новый push — **вы**.

## Что автоматизировано, что нет

| Действие | Авто? |
|----------|--------|
| Сборка на PR (CI) | Да |
| Блок merge при конфликте | Да (GitHub + настройки) |
| Bump 2/3 цифры после merge в `main` | Да |
| Push в `main` без PR | Нет (если включена защита) |
| Обновление `staging` | Нет — PR вручную |
| Прод (1-я цифра) | Нет — [ADMIN.md](./ADMIN.md) |
| CHANGELOG | Нет — вручную / `npm run changelog:append` |

## Labels (GitHub)

`version:minor`, `version:patch`, `version:skip` — для бота версий.

Опционально: `ready-for-staging` на PR в `main`, когда готовы к выкладке на тест после merge.
