# Совместная разработка: ветки, PR, конфликты, тест, прод

## Три уровня, не один срез

| Уровень | Ветка / срез | Для кого | Как обновляется |
|---------|----------------|----------|-----------------|
| **Интеграция** | `main` | Разработчики | Каждая фича через PR; версия 2/3 цифры **растёт автоматически** после merge |
| **Тестовый стенд** | `staging` | Тестировщики, отчёты о багах | **Только вручную**, после **локальных** проверок; на стенде **одна зафиксированная** версия `X.Y.Z` |
| **Прод** | тег / релиз | Пользователи «во вне» | Вручную, 1-я цифра — [ADMIN.md](./ADMIN.md) |

```text
feature/* ──PR──► main ──(бот: версия 0.7.3)──►  локально: build + smoke
                                                      │
                                    «готовы к QA»     ▼
                              PR main → staging ──► деплой стенда
                              (версия на стенде = 0.7.3)
                                                      │
                                              позже: прод
```

**`staging` не копия `main` в реальном времени.** Пока вы не сделали PR «выкладка на тест», на стенде остаётся **прошлый** стабильный снимок — тестировщики не ловят «полуфабрикат» с только что влитой фичей.

---

## Обычная разработка (только `main`)

1. `git checkout main && git pull`
2. `git checkout -b feature/краткое-имя` → код → push
3. **Pull request → `main`**, дождаться зелёного **CI (build)**
4. При **conflicts** — merge недоступен, правите локально → push (см. ниже)
5. **Merge** → бот может добавить `chore(version): bump to v…`
6. Партнёр: `git pull origin main`

На тестовый стенд это **не** попадает автоматически.

## Выкладка на тестовый стенд (осознанный срез)

Делайте, когда на **`main`** уже есть нужная версия (например `0.7.3`) и вы **локально** убедились, что сборка ок.

### Чеклист перед PR на `staging`

- [ ] `git checkout main && git pull` (включая коммит `chore(version)`, если был)
- [ ] `npm ci` (или `npm install`)
- [ ] `npm run build` без ошибок
- [ ] `npm run dev` — smoke: вход, комната, ключевые сценарии фичи
- [ ] Миграции: `npm run db:deploy` на **тестовой** БД стенда (не на прод)
- [ ] В PR указать версию: **«Promote v0.7.3 to staging for QA»**

### PR на стенд

1. GitHub → **New pull request**: base **`staging`**, compare **`main`**
2. Описание для тестировщиков: что проверять, известные ограничения
3. **CI (build)** зелёный, конфликтов нет → **Merge**
4. Деплой с ветки **`staging`** на тест-сервер ([DEPLOYMENT.md](./DEPLOYMENT.md))
5. **Сообщение тестировщикам** (чат / issue), например:

   > Стенд обновлён. Версия для отчётов: **0.7.3** (О программе → номер версии).  
   > В баге указывайте: версию, браузер, шаги.

### Фиксация версии для отчётов (рекомендуется)

После merge PR в `staging`, на коммите стенда:

```bash
git checkout staging && git pull
VER=$(node -p "require('./package.json').version")
git tag -a "qa/v${VER}" -m "QA build on staging"
git push origin "qa/v${VER}"
```

Тег **`qa/v0.7.3`** — точная точка в git, если нужно воспроизвести баг. Номер для людей — тот же **`0.7.3`** в UI.

Повторная выкладка на тот же стенд без смены версии на `main` не нужна; новая выкладка — когда на `main` уже **0.7.4** и снова прошли локальные тесты.

## Конфликты

| Этап | Действие |
|------|----------|
| PR в `main` | GitHub блокирует merge → `git merge main` в feature-ветку, правка, push |
| PR `main` → `staging` | То же; base — **текущий** `staging`, head — **main** |
| Доска (409) | Не git — логика приложения |

Защита веток: [GITHUB_BRANCH_PROTECTION.md](./GITHUB_BRANCH_PROTECTION.md).

---

## Автоматизация

| Действие | Авто? |
|----------|--------|
| CI на PR в `main` / `staging` | Да |
| Bump версии при merge в `main` | Да |
| Обновление `staging` | **Нет** — только PR после локальных тестов |
| Тег `qa/v…` | Вручную (рекомендуется) |
| Прод | [ADMIN.md](./ADMIN.md) |

## Labels

- `version:minor` / `version:patch` / `version:skip` — бот версий на **main**
- `qa-request` (создайте сами) — PR в `main` готов к выкладке на стенд после merge
